# Which Decisions Need to Be Made Again?

> 发布日期:2026-11-22 · [中文](../zh/2026-11-22-%E9%87%8D%E5%A4%8D%E7%9A%84%E6%B4%BB%EF%BC%8C%E5%80%BC%E5%BE%97%E5%8F%8D%E5%A4%8D%E5%88%A4%E6%96%AD%E5%90%97%EF%BC%9F.md) | [English](../en/2026-11-22-which-decisions-need-to-be-made-again.md)

In one WorkArena test, the task is to filter a list of ServiceNow tickets. The instructions already specify the conditions. A browser agent still has to find the hidden menu, enter each condition, and run the filter. The researchers also wrote fixed browser scripts for tasks like this. Both approaches use the website. The difference is who decides what happens next. When I add AI to recurring work, I want to know how many of those decisions need to be made again. Those are the places worth calling the model again. [WorkArena paper](https://arxiv.org/html/2403.07718)

Suppose a batch of records is waiting. After the first one, I'd ask which decisions I can carry over to the next. If all that changes is the name I'm looking for, a program can put the new name into the same filter. If the next ticket asks me to find people who need priority service, I first need to know who qualifies. I might open the same menu both times, but only some of the decisions carry over.

## A new batch can follow the same rule

Suppose you run a small online shop and put together a weekly restocking checklist. You match stock on hand and incoming quantities by product ID, then list the items below their restocking thresholds. Inventory changes every week and some items get discontinued, but product IDs have a clear meaning and someone maintains the threshold table. As long as those conditions hold, a program can read the new data each week and apply the same rule. A fixed browser script can even download the reports. The shop platform might also offer an API, a way for a program to request data directly from the service. In this hypothetical shop, if the API returns the quantity on hand for each product, the program can read that number without downloading the report. [Beyond Browsing paper](https://aclanthology.org/2025.findings-acl.577.pdf)

It's a bit like printing a batch of address labels. Every label has a different name, street, and house number, yet you can use the same process to turn a spreadsheet into a stack of labels. A printer will happily produce a label with no house number, so you need to pull that row aside. The same applies to missing entries on the restocking sheet. An explicit zero can go into the calculation. A blank calls for a check to find out whether the data is missing or the blank means something else. Address labels usually come from a snapshot. Inventory can change between two exports, so the restocking sheet also needs an agreed point in time for the data.

I would ask a simple question about the work in front of me. Do we have a new batch of numbers, or has the basis for choosing which number to use changed too? If stock quantities change, run the usual calculation. If a supplier redefines incoming quantity to count only goods already dispatched, a formula can still run smoothly while the team needs to decide which goods should count. A model can help find the notice and identify the affected rows. Once the team agrees on the definition, it can put the rule back into the spreadsheet for next week.

WorkArena offers a useful distinction here. In 2024, Drouin and colleagues wrote Playwright solutions for 33 types of ServiceNow tasks. Playwright lets a program operate a browser, including clicking menus and filling forms. In Table 2, the best browser agent tested averaged 42.7% success on those tasks. The scripts were there to establish that the tasks had executable solutions. Maintenance costs over time were outside this single-platform experiment. I would use it as a reason to ask whether I can write down a fixed solution for my own work, then calculate separately whether it's worth maintaining. [WorkArena paper](https://arxiv.org/html/2403.07718)

## An API can save navigation. The fields still need checking.

In their 2025 WebArena study, Song and colleagues compared three approaches using the same GPT-4o model. Average success was 14.8% with browsing alone, 29.2% with API access alone, and 38.9% with both available. One task asked how many commits, or recorded changes, a contributor had made to a software repository. The browser agent took 15 steps without finding the information it needed. The API agent retrieved the commit records and counted them by author. These were text tasks on controlled websites. The API agents still chose what to call as they worked, and the authors added some interfaces for the experiment. [Beyond Browsing paper](https://aclanthology.org/2025.findings-acl.577.pdf)

What matters to me in that example is that once you can read the commit records field by field, finding them and counting them become two steps you can check separately. Back at the shop, you can match the data by product ID even if the website moves its menus every week. An API can also keep working perfectly well while giving you a field that means something different from what you need. Available stock may already exclude the units reserved for unshipped orders. Deduct them again and the program understates your inventory. A smooth run can make that error quieter.

The WebMall project by Steiner, Peeters, and Bizer compared several ways to access simulated shops. The regular store APIs used different parameters and field names. Another interface, NLWeb, returned search results using the same product fields across stores. For example, offers appeared in a consistent place, with the amount and currency listed separately. The study used shops set up for the experiment. What I'd take from it is to pick one real business record before connecting a service and compare what its fields say with a report you already use. A common format saves a round of translation. That comparison still matters when you need to establish what a field means for your business. [WebMall project page](https://wbsg-uni-mannheim.github.io/WebMall-Interfaces/)

Even when the product IDs match, there's one more question. Do the records cover the same batch? If this week's stock report is still updating, the program might read last week's complete file and produce a perfectly presentable sheet. For a weekly report, I'd put the source and date beside the result. A colleague who asks about a row can then look at the records used at the time and work out whether the rule was wrong or the data was pulled too early.

## Sometimes the page is the only way in

A small team may have nothing more than a regular account, with restocking notes available only on the website. That's a useful job for a browser agent. Think of a supplier's note saying that one color ships as usual and another is on hold until further notice. Someone needs to see the note before deciding which items to set aside. If the request comes up just once, spending half a day looking into an integration may be more work than looking at the page. Letting a browser agent find the original note for a person to make the call can already save a fair amount of searching.

The 2025 MCPWorld preprint examined a related question. MCP lets an agent call functions an app makes available, such as checking the app's current state. Across 201 tasks in open-source desktop apps, the configuration the paper calls MCP-Only succeeded in 53.23% of runs. The authors attributed nearly half of that configuration's failures to the available MCP tools lacking a function the task required. [MCPWorld preprint](https://arxiv.org/html/2506.07672v1)

The graphical configuration succeeded in 70.65% of runs. The agent could click buttons on the screen, edit files, and use a shell, where it could type a command to read a file without clicking to open it. The hybrid configuration offered those tools alongside the MCP tools, letting the agent choose at each step. It succeeded in 75.12% of runs. The experiment used specific desktop apps and one agent framework. Because the graphical configuration also had shell access, the figures can't tell us how much the screen controls contributed on their own. [MCPWorld preprint](https://arxiv.org/html/2506.07672v1)

I'd choose based on what's missing. For a fixed field you need every week, it's worth checking the official exports or asking the vendor for a way to retrieve it. For a one-off notice, a browser agent can find it and show the source for someone to read. Sometimes the team hasn't made the rule itself. Does a two-day delay count as urgent? More text from the page can help the discussion, and someone still has to decide the conditions for urgency. Treat all three gaps as a shortage of model intelligence and you may just pay for more industrious scrolling.

## One disruption can show you what checking costs

Kara and colleagues used WABER to introduce disruptions including pop-ups into WebArena. They tested two browser agents on selected Reddit and shopping tasks. On the Reddit subset, AWM's success rate fell from 60% under ordinary conditions to 20% with pop-ups. Those figures describe specific test tasks and deliberately introduced pop-ups. What I'd borrow is the idea of picking one disruption that could actually happen in my own work and seeing what the system hands me at the end. [WABER paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2025/04/134_WABER_Web_Agent_Benchmarki.pdf)

For the restocking sheet, I'd try a run where one supplier's data hasn't arrived. It's easy to miss a blank in a spreadsheet. If the assistant fills in a zero and marks the whole sheet complete, I have to go back to the source material and check it item by item. If it groups the affected products, names the source that's missing, and gives me verifiable results for the rest, I can spend my review time where it matters. I would ask the same question of a script and an AI agent. Can I see what's missing from the result?

I'd track two kinds of time. The first runs from starting the tool to getting the result. The second is how long I spend checking what I can use and filling the gaps in what I can't. For a one-off, it can be enough for those two together to beat doing the job by hand. For weekly work, setup and maintenance count too. If I still open both source files and check them from the beginning most weeks, the downloads and joins may be easier, but the review I'm left with weighs about the same. A slower process that reliably identifies the rows I need to see can free me to do something else while it runs.

This also changes how I'd think about mistakes. If the tool plainly reports that a source is late, I can decide whether to handle the products I have data for or wait for the rest. If it quietly uses last week's data and hands me what looks like a complete result, I don't even know when to step in. I'd record those outcomes separately in a trial. One leaves me a choice. The other allows a gap I could have caught early to carry forward into the rest of the work.

## Save one rule for a job you do every week

I'd suggest a small trial. Pick a recurring job with a result you can see, and try it on an old set of inputs. The restocking sheet has a previous version to check against. You might have a weekly report or a checklist for planning next week's work. Narrow the task to something you can review today. Use a copy for the first comparison and stop at a draft you can check.

1. Write the rule that determines the result in ordinary language. On the restocking sheet, the product ID, current stock, incoming quantity, and restocking threshold tell you whether an item belongs on the list. Write down one condition that puts the rule on hold, such as a missing supplier file. If you can show how the rule works on two old rows, you have a starting point.
2. Run it each way with the same input and the same criteria for success. Ask a browser agent to collect the data through the existing website. Then try the export and spreadsheet formulas you already have, or ask AI to turn the rule you've written into fixed steps. A previous sheet you've checked can serve as the reference. Compare the products listed, their quantities, and the source dates. Record the time you spend preparing, running, and checking each version. If you only have one route, use the same criteria to compare it with one manual run.
3. Remove one piece of data that should be present from your copy and run it again. Check whether the result flags the missing input, lists the affected rows separately, and retains the parts that still have a basis. Try the same input once more and make sure a change in wording doesn't add a row to the count. Then weigh the initial setup time against how often you expect to use the process, and leave some time for maintenance when things change. If the fixed steps save time only when everything goes smoothly, give them a smaller part of the job.

Afterward, ask yourself what happens when next week's sheet arrives. Will I still have to decide how each row should be calculated, or will I only need to deal with the rows where the basis for the decision changed? If the issues mostly come down to IDs, blanks, and dates, writing those rules into the spreadsheet or the workflow may already give you something worth handing to someone else. If different sources keep giving different accounts, ask AI to put the statements and their sources side by side. When the same disagreement recurs, see whether you can carry today's decision into next week.

Give yourself one less thing to figure out next week.
