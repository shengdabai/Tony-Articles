# A Different Way to Operate Still Has to Pick Up Where the Work Left Off

> Published: 2026-11-21 · [中文](../zh/2026-11-21-%E6%8D%A2%E4%B8%80%E7%A7%8D%E6%93%8D%E4%BD%9C%E6%96%B9%E5%BC%8F%EF%BC%8C%E4%B9%9F%E5%BE%97%E6%8E%A5%E4%B8%8A%E5%90%8C%E4%B8%80%E4%BB%BD%E8%BF%9B%E5%BA%A6.md) | [English](../en/2026-11-21-resume-from-confirmed-state.md)

---

A summary of a browser automation retrospective raises a question. Suppose you give a program a list of records to enter on a website. It stops partway through, with the page still open. The AI can pick up the mouse, but which record should it enter next? If the last one went through, another click could create a duplicate. My suggestion is to check which records were saved and let the AI resume with one you can confirm is missing.

If you organize files, enter records, or update a batch of drafts every week, this is a more concrete question than which model can click a mouse. You can ask AI to run repetitive operations through a program. You can also ask it to look at the screen and work through menus as a person would. The decision to make in advance is where the second method should start when the first leaves you with a partial result. That choice affects whether you can hand off the work or still have to check it all from the beginning when it comes back.

## The Hardest Progress to Work With Is the Progress You Can't Confirm

Suppose you prepare chapters for several recordings every week. You have already written down each chapter title and start time. The deliverables are an editable audio project and a text export someone can copy into a publishing page. With the titles and times settled, a program can write them from your list and save you the trouble of locating and entering each one. Some of the work still calls for a look at the screen. Are the markers crowded together? Can an editor read them easily when opening the project? The same AI can do both kinds of work. It helps to describe what counts as finished for each.

Suppose the program sends a save request and never hears back. The project may have saved and the acknowledgment may have gone missing. The changes may still be open and unsaved. Or the chapters may be in the saved project while the export never happened. Open the editor and you might see the chapters on the timeline. That tells you what's visible right now. Finding out what survives reopening the project, and which run produced the text in the delivery folder, takes separate checks.

This distinction came up in a desktop experiment. In a 2026 preprint, Xiao Zhou and colleagues describe an Audacity task in which a screen-only agent created the label track and its required chapter labels, operated the export dialog, and reported that it was done. The verifier could find no exported text file. The same study gives an example in the other direction. On another chapter-label task, the screen-only agents could complete the job through Audacity's built-in menus, while the tools available to the command-based agents could not reliably write the labels to a project state the verifier could read. The two tasks concerned export and label creation, respectively. I put them together because they raise the same question. What part of the result are you looking at when you say how far along the work is? [GUI vs. CLI, Appendices A.1 and A.4](https://arxiv.org/html/2606.24551v1)

The study covered 440 desktop tasks. To count as complete, a task had to pass every check on its outcome. The strongest screen-only configuration passed 59.1%, and the strongest configuration using the original command tools passed 48.2%. Those two configurations used different models. The researchers looked at what the checks required, added missing operations to the command tools, and tested them on the same tasks. The pass rate rose to 69.3%. That shows how many of the original tasks the repaired tools could handle with the requirements known in advance. How often they would succeed on a new job is still an open question. If a tool says it supports exports, I'd try a sample and see whether the recipient can open the file in their own software. [GUI vs. CLI, Sections 4, 5, and 7.1](https://arxiv.org/html/2606.24551v1)

Think of a print shop partway through a batch of binding orders. The machine stops. Before the next person presses Resume, they need to work out which jobs on the counter are already bound and which are still loose sheets. Numbered finished copies are easy to identify. A mixed stack of loose pages takes a fresh count. The program's acknowledgment is like the machine's progress display. The files in the delivery folder are like the finished copies on the counter. In both cases, the person taking over needs to identify the work that really is complete. A digital file adds a wrinkle the counter doesn't show. Last week's file can still be sitting in exactly the same place under exactly the same name. You have to check its contents and which job it belongs to. Existence tells you only that there's a file there.

## How to Hand Off Between Two Ways of Doing the Work

I'd choose how to perform an operation and how to confirm its outcome separately. If writing the chapters stalls, leave the original window alone. The next editor will receive the project file in the delivery folder, so I'd copy that file from disk, open the copy independently, and compare its chapter labels one by one with this week's list. Even if every title is visible in the original window, check which titles you can read in the copy and where each chapter starts. If the saved project matches and the text is missing, pick up at the export. If you can identify exactly which labels are missing, fill those gaps. If you can't tell whether the file belongs to this week's job or an older one, settle that question before making another change.

There's an easy detail to miss. You may find a text file with the right name and see that every title is present. That can feel sufficient. If the only edit this week was to a chapter's start time, an old export with all the right titles will pass that check. For this hypothetical deliverable, compare the titles, order, and times together. Then think about who uses it. The editor needs to reopen the project and keep editing. The publisher needs to open the text and copy the chapters. The closer your checks are to what those people do next, the easier it is to see what evidence to keep.

Keeping two ways of working available can help. Yunhe Yan and colleagues tested 201 desktop tasks in MCPWorld using the same agent framework and Claude 3.7 Sonnet. A graphical user interface (GUI) lets the AI look at menus on screen and click buttons. An application tool lets a program ask the software directly to do something, such as create a page with a specified name. The hybrid configuration, which offered both routes, achieved a 75.12% success rate. The GUI configuration reached 70.65% and the application-tool configuration reached 53.23%. One detail matters when reading those labels. The GUI group could also enter text commands to tell the computer what to do. The finding gives you a reason to try both routes in your own software. The average leaves open the question of when, in your workflow, to switch. [MCPWorld, Sections 4.1 and 4.2 and Appendix C.1](https://arxiv.org/html/2506.07672v1)

You might say that if the AI has both options, you may as well let it find its own way. That makes sense for some one-off tasks. If you only want a look at how the chapters might be arranged, you can experiment freely and close the copy when you want to start over. When the machine produces a batch every week, you care what it leaves behind after taking a wrong turn. In Yueqi Song and colleagues' web experiment, the agent that could switch between browsing and direct website functions performed better overall, but the authors also document an exception. A GitLab query had a direct route to the required information. The hybrid agent chose to browse and failed to finish. This was one case on a WebArena test site, and the browsing agent worked with a structured description of the page's controls. Even when both routes are available, choosing one is still work. [Beyond Browsing, Results and Case Study 2](https://yueqis.github.io/API-Based-Agent/)

How many more jobs can the AI finish with an extra set of tools? Hongrui Jia and colleagues compared two ways of running o3 on 361 desktop tasks in OSWorld-MCP. With up to 15 steps per task, o3 completed 8.3% using screen actions alone and 20.4% when it could also use a curated set of programmatic tools. With up to 50 steps, the figures were 12.8% and 25.2%, respectively. Each figure is an average over three runs per configuration. On these tasks, the group with the extra tools completed more work at both step limits. [OSWorld-MCP, Sections 3.3, 3.4, and 4.2, Table 1](https://arxiv.org/html/2510.24563v1)

Table 1 reports how often the AI completed a task, a tool-choice score, and the average number of steps per task. The tool-choice score is the share of all tasks where the agent both succeeded and made the choice the researchers expected: it used a tool when the researchers judged one helpful, and skipped tools otherwise. The table gives no time for a recipient to check the files. [OSWorld-MCP, Sections 3.4 and 4.2, Table 1](https://arxiv.org/html/2510.24563v1) When the files come back to you, I'd record three times in your own trial: how long it takes to find a tool, switch to it, and inspect the result. If you can already export text reliably from a checked project, I'd keep that step and practice deciding whether you can resume there after an interruption.

Sometimes the consequences of a switch show up right away. A program closes a dialog, and the button you saw a moment ago may have moved. The project page for Hybrid Computer Use, from Haoqing Wang and colleagues, shows how the system checks the live window layout before sending mouse input. In its illustrated example, closing a panel puts Delete where Save was in the old screenshot. The system blocks the click and returns a fresh screenshot. The check concerns where the next input would land. Back in the audio example, check the current project and dialog before clicking Export. Afterward, check the text separately. Skip either check and you may continue on the strength of the wrong evidence. [Hybrid Computer Use, layout guard illustration](https://microsoft.github.io/Hybrid-Computer-Use/)

## Try It With One Interruption

Here's the exercise I'd suggest. Pick a job you'll do again next week. Use copies you can discard, and keep the scope to one recording and its corresponding text export. The first method gives no clear acknowledgment. Can the second determine where to resume using only what it has available? You can prepare copies in an interrupted state by hand. There's no need to make the software actually crash. You'll know what happened to each copy, which gives you a way to judge whether the AI has read the situation correctly.

1. Write down the delivery conditions first. Include the audio project, the matching chapter text, and the titles, times, and order that need to agree. Give the trial its own output location so an older file with the same name doesn't count automatically. The example has one more condition, readability when the project opens. Take a look and keep that judgment with a person.
2. Prepare two copies in different states. In the first, the project is saved and the text is missing. In the second, the project is incomplete and an old export with the same name sits beside it. One chapter time in that export differs from this week's list. Tell the AI the previous operation ended without a clear acknowledgment. Before it acts, ask it to list what it has confirmed, what is still unknown, and which step it plans to pick up. Give it only the materials and access it needs to check the results independently.
3. Let the AI try to resume on the copies, then check both against the same list. It should generate only the missing text for the first copy. There's no need to write the labels into the project again. For the second, it should identify the old export and find out what the project is missing before making changes it can target with confidence. If something doesn't add up, record where it stopped and what information would let it continue. You can repeat the trial with the copies in the opposite order to see whether it merely learned how to answer the first case.
4. Record your own time after the run. Track how long it takes to recheck everything, inspect the known gaps, and fix any duplicates. If using a different route still leaves you checking from scratch, start by automating one small segment, such as exporting text from a project you've already checked. If the job rarely comes up and it's quick to do by hand, keep the written delivery conditions and use them the next time you run through it.

Ask yourself one question after the trial. If I wake up tomorrow to a message that the job stopped and a deliverable that looks complete, what would let me decide whether to continue, start over, or leave it alone? If your answer is to open everything and check it one item at a time, the best thing you can change today may be to leave enough evidence in the deliverables for someone to see how far the work got. One point where you can reliably resume is plenty to start with. Try it on a copy before the day you're in a rush to deliver.
